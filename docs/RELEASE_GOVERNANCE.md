# Local release governance (schema 1.0)

Release eligibility and human approval are separate. The foundation gate evaluates only synthetic arithmetic fixtures; an approval cannot authorize a real agent, finance advice, publishing, or a production run. `AgentRunner` keeps its existing explicit fake-only test/demo restriction.

A `ReleaseCandidate` JSON manifest contains `schema_version: "1.0"`, `agent_name: "foundation"`, the default versioned `ReleasePolicy`, and an `evidence` map with exactly `dev`, `holdout`, and `prod_regression`. Each entry has a local `path` and immutable `bundle_hash`. A path may reference an experiment bundle or a complete verified Phoenix offline export directory. Generate experiments with the three commands in [FOUNDATION_EVALUATIONS.md](FOUNDATION_EVALUATIONS.md), then construct the manifest using `ReleaseCandidate` and `EvidencePin` from `app.release.models`. Paths and experiment hashes are part of the candidate identity; moving evidence creates a different candidate.

Readiness only:

```sh
.venv/bin/python -m app.release.check --agent foundation --candidate data/candidate.json --registry data/state.db
```

Exit 0 means the exact candidate is already human approved and still passes its evidence checks. Exit 1 means blocked or awaiting human action, including `REQUIRES_BOOTSTRAP_APPROVAL` and `ELIGIBLE`. Exit 2 means invalid or missing evaluation/configuration evidence. There is no approval command, worker bypass, critical-regression override, or evaluation-degraded mode. Output contains statuses, reason codes and hashes, without private examples or reviewer identities.

All splits must have all required members on every repeat. The gate binds dataset membership and expected labels, actual output/artifact pins, schema, installed prompt, evaluation policy, evaluator implementation, synthetic judge/calibration, and exact shared configuration/model/code provenance. It recomputes every deterministic and synthetic rubric result. Each required metric must pass for every example/repeat; missing values, judge-only success, incorrect averages and critical false acceptance cannot promote. Regular files, complete offline exports and mixed candidates use the same pure three-split snapshot validator, including rights/adjudication, row identity, reference resolution and event/evidence isolation. Offline artifacts are captured once, and the exact checksummed bytes are evaluated; files are never reopened after verification. Complete restricted offline exports work after the original dataset directory is gone. Required installed evaluator/calibration and policy files must remain available and match their hashes. A local export is evidence, not permission to skip evaluations.

The first complete candidate remains `REQUIRES_BOOTSTRAP_APPROVAL`. `ReleaseService.approve(candidate_hash, principal, expected_version, bootstrap, idempotency_key)` is an internal seam for the authenticated Task 12 route. Its constructor takes a trusted `current_session_verifier(principal)` callable, defaulting to denial. Only the literal result `True` for a current allowed human is accepted; a `Principal` object, session string, truthy object or agent identity alone grants no authority. Real session verification and HTTP routes are not implemented here. Tests inject a trusted fixture only. Approval starts with expected version 0 and explicit `bootstrap=True`; later versions require `bootstrap=False` and a comparable pinned human-approved baseline.

Current-session verification occurs before receipt lookup and immediately before mutation. Approval keys are scoped to provider/numeric account/operation; their fingerprints bind the candidate's exact configuration/experiment manifest, expected version and bootstrap flag. Identical retries return the original immutable receipt before current-version/evidence mutation checks, with no duplicate event or baseline change. Changed payloads conflict. Revocation removes execution authority but preserves the pinned historical baseline and immutable receipt. Replaying an old receipt does not reactivate it; query `active(agent_name)` separately for current authority. Re-bootstrap cannot erase approval history.

`app.evals.compare --baseline approved --registry data/state.db` opens an existing registry read-only and resolves the exact historical approved baseline for the candidate split, including after execution revocation. It never creates a missing database, runs migrations or changes permissions. A checked-in fixture is never a registry approval. Changed datasets or evaluator policies are incomparable and require a reviewed common rerun; this slice provides no rerun/adjudication approval bypass.

`require_approved` is a future execution guard that checks exact active pins and live required validators. Its only currently supported mode is an explicitly named `foundation_demo`. The default production mode denies synthetic evidence; no real execution is enabled. Callers must use server-resolved current configuration pins and trusted live validator results. The guard does not authenticate callers or replace `AgentRunner`'s separate restrictions.

The five immutable registry tables use `WITHOUT ROWID`, removing hidden `rowid`/`oid`/`_rowid_` replacement identities, and reject conflicting logical-key inserts, including SQLite replacement writes with recursive triggers disabled. Deliberate check/annotation retries use transactional explicit lookups instead of conflict inserts. Feedback references local annotations by path and hash. `queue_feedback` verifies those bytes and creates an immutable quarantine receipt with privacy, rights and adjudication reviews reset to `PENDING`, even when supplied annotations claim clearance. It never writes a dataset. There is no feedback promotion workflow yet; future reviewed data must become a new version while maintaining an untouched holdout split. Keep the business SQLite database and local evidence directories restricted to authorized operators; their contents are privileged, and hashes do not authenticate a hostile local database owner.

Versioned contracts are exported to `schemas/v1/releases.json`. Release policy `foundation.release.v1` and evaluation policy `foundation.v1` remain synthetic-only. No prompt or real-agent quality claim is introduced.
